# Activating, changing and operating the enterprise — customer scenarios

Required future UX; none of these screens or runtime capabilities is delivered
by this specification checkpoint. [Engineering handoff](../production/DOMAIN-FIXTURE-HANDOFF-17.md).
All 480 original acceptance scenarios now have concrete expected observations;
implementation, independent review and real qualification remain ahead.

## 1. “Can this part of my business actually operate?”

A founder or migration owner opens Business coverage. They see the inventory date
and six separate measures: discovered, described, constrained, runnable, tested,
and observed outcomes. Clicking a gap opens the exact activity, source, owner and
next action. Imported diagrams can make description coverage high without making
anything runnable. There is no single misleading “enterprise 100%” score.

The owner requests activation of the fulfilment scope, reviews eligible people/
agents, resources, process version, checkpoints, tested controls and real run
evidence. An independent accountable reviewer accepts that exact scope. A separate
Activate action enables eligible work; it does not grant blanket permissions.

If a critical activity is discovered during review, the request says why it is
stale and offers reassessment. If hypercare finds a failed control after activation,
affected new work is contained, accepted remote work stays tracked, and the old
sign-off remains visible as history. The user is never told that changing the
design has undone a shipment or payment. T-120, T-109, T-119, T-127.

## 2. “I changed ownership from the organisation map. What else changes?”

The designer selects a process owner on the map, edits it and opens impact preview.
The same operation is available from chat, form, matrix, bulk edit and API. Source
connectors, migration, workflow results and accepted learning reach the same
validated path; observed facts cannot silently approve themselves.

The preview names the changed field and paths to affected role instructions,
constraints, Sentinel claims, SDLC context/evaluations, approvals and queued work.
It distinguishes queued, running and completed work and identifies reviewers.
An incomplete impact calculation cannot enable protected Publish. Conflicts have
concrete compare/repair actions; returning to the map retains the selection.

After valid publication, old protected approvals are unusable immediately.
Some read views may still show an explicit “updating from version 7 to 8” banner;
they cannot authorize actions from old data. Historical runs keep version 7.
Moving a box on the canvas, by contrast, changes layout only and does not invalidate
unrelated approvals. T-121–T-124, T-90–T-95.

## 3. “Our ERP says something different. Which fact is true?”

The source view distinguishes accepted owner assertion, current observed evidence,
proposal, contradiction, stale evidence and missing information. The user can see
the source revision, observation time, accepted baseline, freshness deadline and
responsible repair owner. A missed event is repaired through manifest reconciliation;
it is not hidden because the latest event number is large.

If the ERP shows one-person release while policy requires two people, OrgWard
creates a finding and proposal. It does not change policy to make the bypass green.
The authorized owner reviews the correction; Sentinel and affected SDLC evaluations
recompute against matching inputs. Old evaluations remain inspectable. T-124.

## 4. “We have our own inspection process—not one of your templates.”

A customer designer defines a versioned Inspection concept, typed sample reference,
temperature field with units, decision choices, relation, permitted constraint and
form. They attach a governed request-inspection action using a supported adapter.
The customer cannot redefine core permissions or upload authorization code.

The process editor supports equivalent diagram and structured forms: intake →
agent classification → human approval → external request. Add a bounded rework loop
or substep, specify criteria, preview impact, simulate safely and publish a new
version. Publication does not activate execution. Existing runs stay pinned unless
an eligible checkpoint migration is separately reviewed.

If a new schema requires a calibration reference, migration preview lists affected
objects and blocked missing values. It never invents references or rewrites old
case history. A provider failure shows pending reconciliation, not “try again” that
could duplicate a real operation. T-125 and the mandatory WF obligations.

## 5. “I just need to do my work, not learn the architecture.”

A worker opens My work, sees the assigned inspection, deadline and required output,
completes an accessible form and saves partial work if interrupted. No map is
required. The same activity and evidence can also be opened from a process map.

The next human checkpoint cannot be skipped by pressing Done. Missing performer,
unsupported physical adapter or missing required output stays blocked with an
owner and recovery action. A technician's signed/photo attestation is labeled as
such, not advertised as sensor proof or independently tested business outcome.

Duplicate form submissions and restarted timer workers preserve one logical
result. Ambiguous local times show the selected timezone/occurrence. Reopening
the page restores persisted progress rather than restarting external work.
T-126, T-127, T-98.

## 6. “How does this relate to a real SDLC?”

An architect accepts a business change; impact exposes affected system intent,
requirements, evaluations and operational dependencies. The engineering owner
opens a versioned SDLC process, chooses the eligible workflow and inspects budgets,
tools, criteria and required independent reviewers.

An example process is context → requirements → design → implementation → tests →
independent review → staged release → measured outcome. It is an editable template,
not a hardcoded sequence. The owner can insert a security-review substep or bounded
fix/test loop through either editor. New runs use the approved new definition;
already running attempts retain their pinned version and visible migration options.

Agents produce actual code/artifacts in isolated execution, run prescribed checks
and report evidence. A failed evaluation routes the defined rework path within
shared limits; it does not give the agent extra authority. A business change during
the run can invalidate context and stop the next protected effect even while the
UI catches up. Independent review and current broker checks precede deployment.
Sentinel observations after deployment may propose another governed correction.
Successful deployment and successful business outcome remain separate claims.

## 7. “Can my enterprise safely use the released system?”

The release/support view names supported installations, regions, providers, limits,
modules, tested combinations, evidence dates and unresolved limitations. Self-host
success does not imply managed SaaS isolation or public-edge qualification.

Independent customers/operators must demonstrate new and migrated businesses,
actual work, changes through every entry point, configurable workflow editing,
Sentinel-to-SDLC correction, export and restore. Noisy-tenant, support abuse,
failover, duplicate event, stale review and unknown-effect tests are required too.
Any mandatory unrun/failed result prevents full readiness. Newly discovered gaps
reopen scope/evidence; they are not removed from the denominator. T-128–T-132.

## What happens next

The scenario-definition layer is now complete for the original 132-task plan.
This does not mean “hand each task to an agent and trust the result.” Each bounded
slice still needs integrated exact contracts, complete seed datasets, independent
observation tests and a legitimate review before coding. The first candidates are
foundation contracts and truthful demonstrator states (T-01/T-02), followed by
dependency-respecting end-to-end journeys. No customer credentials, permissions,
industry decisions or live effects are invented to make a checklist pass.
