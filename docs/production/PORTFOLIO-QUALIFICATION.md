## Coverage strategy beyond enumerated examples

The 20 F-families enumerate enterprise forms, identity, concurrency, failures, time, scale/accessibility, truth/uncertainty, external effects, scope/federation, agent attacks, data trust, SDLC variations, authority, business exceptions, extension/interchange, economics, perspective consistency, policy lifecycle, installation and Sentinel fidelity. Each feature task inherits identity/isolation, replay/concurrency, failure/restart, migration and accessible-UX cases even if a family lists only the principal owning tasks.

For a supported release create a machine-readable test-run matrix selecting concrete variants, not just family names. Cover each applicable value and all pairwise interactions; the eight explicit X-intersections and all destructive/high-impact combinations require targeted multi-factor tests regardless of pairwise generation. Record generation seed, constraints, excluded combinations, risk rationale and test IDs. Unsupported combinations are visible support limitations, not passed or silently omitted. A mandatory baseline feature cannot be marked N/A to ship the full portfolio.

Additional discovered scenarios get a stable requirement/fixture, mapped source intent, owning task and supported-release decision. A new scenario does not rewrite historical receipts or reset fixed gate denominators. Do not claim a finite scenario catalogue proves “all possible enterprises”. It supplies a method for preserving new cases without erasing previous intent.

The twenty-four ES contracts in ../product/ENTERPRISE-SCENARIOS.md are also mandatory for their explicitly stated support class. Include their actual actor/trigger/outcome/adverse-case fixtures in the run matrix; model/review support is not silently upgraded to live ERP, HR, accounting or regulated-action execution. All supported adapter/domain-pack effects require their own qualification and current authority.

## Evidence, adjudication and task handoff

Every receipt binds revision/tree digest, schema/module/profile/provider versions, fixture manifest, principal roles (no secrets), commands, raw results, screenshots/recordings where relevant, timestamps, measured values and unresolved defects. Screenshots supplement persisted backend assertions. Include successful, denied, concurrent and recovered paths. Real integrations are mandatory where the story requires them; mocks prove only contract tests. Evidence references must resolve under ops/checks and must not merely contain a promise to run later.

Before coding each task, create its executable contract and a bounded implementation package: affected files/aggregates, API examples/errors, transaction/outbox boundary, indexes, permission matrix, migration/rollback, UI state transitions and named test fixtures. Shared domain definitions in ENTERPRISE-MODEL and module boundary contracts are binding. Split work too broad for one verifiable increment into child tasks without discarding parent acceptance or bypassing dependencies. An ambiguity affecting authority, safety, data loss or semantic compatibility is a blocking decision—not permission for a coding agent to improvise.

Close a task only after its own criteria and dependency receipts pass. Close a module only after source-specific and integration qualification. Close full portfolio only when all PF requirements, source rules/acceptance, PC mutations, F coverage, X intersections and PQ journeys have actual passing evidence and all P/E gates satisfy their original acceptance. Independent security and customer/operator review remain required: task counts and LLM-authored tests alone cannot assure enterprise readiness.
